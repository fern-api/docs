Fern generates API Reference documentation from a [GraphQL schema](https://graphql.org/learn/schema/). Add your schema file to your Fern project and Fern renders queries, mutations, subscriptions, and types as an interactive reference.

## Configuration

<Steps>
<Step title="Set up your project structure">

Add your GraphQL schema file to your `/fern` directory and create a `generators.yml` that references it:

```yaml generators.yml
api:
  specs:
    - graphql: plants.schema.graphql
      name: Plants
      origin: https://api.example.com/plants/graphql
```

</Step>
<Step title="Add the GraphQL Reference to your navigation">

Add `- api: API Reference` to your navigation in `docs.yml`:

```yml docs.yml
navigation:
  - api: API Reference
```

</Step>
<Step title="Customize the layout">

For a full list of configuration options and layout customizations, see [Customize API Reference layout](/learn/docs/api-references/customize-api-reference-layout).

Queries are grouped in the sidebar by their parent field, so related queries sit together under the field they hang off of. Mutations and subscriptions stay flat.

</Step>
</Steps>

### Include more than one GraphQL Reference

To include multiple GraphQL definitions in your documentation, use the `api-name` property. The `api-name` corresponds to the folder name containing your GraphQL schema.

<Files>
  <Folder name="fern" defaultOpen>
    <File name="fern.config.json" />
    <File name="docs.yml" />
    <Folder name="plant-graphql" defaultOpen>
      <File name="schema.graphql" comment="Plant GraphQL schema" />
      <File name="generators.yml" />
    </Folder>
    <Folder name="garden-graphql" defaultOpen>
      <File name="schema.graphql" comment="Garden GraphQL schema" />
      <File name="generators.yml" />
    </Folder>
  </Folder>
</Files>

```yaml title="docs.yml"
navigation:
  - api: Plant GraphQL API
    api-name: plant-graphql
  - api: Garden GraphQL API
    api-name: garden-graphql
```

### Provide custom examples

Fern generates examples for your GraphQL operations. To display your own instead, add an `examples` file to the spec entry:

```yaml generators.yml
api:
  specs:
    - graphql: plants.schema.graphql
      name: Plants
      examples: plants.examples.yml
```

Each top-level key in the examples file names an example and supplies the `query` to display, the `variables` it takes, and the `response` it returns:

```yaml plants.examples.yml
Get a plant by ID:
  query: |
    query GetPlant($plantId: ID!) {
      plant(id: $plantId) {
        id
        name
      }
    }
  variables:
    plantId: plant_123
  response:
    data:
      plant:
        id: plant_123
        name: Monstera deliciosa
```

### Configuration properties

<ParamField path="api.specs[].graphql" required>
  Path to your GraphQL schema file. You can include multiple GraphQL specs if your project exposes more than one GraphQL API.
</ParamField>

<ParamField path="api.specs[].name">
  Name of the folder that operations from this spec appear under in the API Reference sidebar. Use this to group related GraphQL operations together. Specs that share a `name` are compiled into a single schema, as described in [Multi-file and federated schemas](#multi-file-and-federated-schemas).
</ParamField>

<ParamField path="api.specs[].examples">
  Path to a YAML file of custom examples for the operations in this spec. See [Provide custom examples](#provide-custom-examples).
</ParamField>

<ParamField path="api.specs[].origin">
  URL of your GraphQL API endpoint. Fern performs [introspection](https://graphql.org/learn/introspection/) against this endpoint to fetch the schema. When set, [running `fern api update`](/learn/cli-api-reference/cli-reference/general-commands#fern-api-update) updates the local schema from this endpoint.
</ParamField>

## Types section

Every GraphQL API Reference includes a **Types** section. Each named type in the schema gets its own page, grouped within the section by kind:

- Objects
- Inputs
- Enums
- Scalars
- Interfaces
- Unions

A kind with no declarations in the schema produces no group. Type pages live at `<api>/types/<kind>/<type-name>`. All GraphQL specs in an API section contribute to a single shared Types section, which sits at the API root rather than under a subpackage.

Operation-namespace types are not documented as standalone types. A grouping type such as `CheckoutMutations` in `Mutation.checkout: CheckoutMutations` exists only to namespace operations, and those operations are already documented individually.

Interfaces get their own page in the **Interfaces** group, rendered with their own set of fields and the list of types that implement them. Each implementing type lists the interfaces it implements. Before CLI 5.109.0, an interface with implementing types was rendered as an undiscriminated union shape instead of a first-class interface page.

Custom scalars such as `DateTime`, `URL`, and `EmailAddress` are emitted as named alias types in the **Scalars** group, and every reference to them in the documentation links to their type page.

Field-level arguments on nested object types are documented, not only arguments on top-level query and mutation fields. Given the following schema, the `Image` type page documents all three arguments on `url`:

```graphql
type Image {
  url(width: Int, height: Int, lossy: Boolean): String!
}
```

## Multi-file and federated schemas

GraphQL schemas whose SDL is split across multiple files are supported. Specs that share a `name`, or that all declare no `name`, are compiled into a single schema. Federated subgraphs that reference types owned by sibling files and extend the same `Query` and `Mutation` types are therefore documented as one API:

```yaml generators.yml
api:
  specs:
    - graphql: ./graphql/products.graphql
      name: Storefront
    - graphql: ./graphql/reviews.graphql
      name: Storefront
    - graphql: ./graphql/users.graphql
      name: Storefront
```

### Federation directives

Composition directives are ignored: `@key`, `@external`, `@link`, and federation v2.9 directives such as `@cost`, `@listSize`, `@context`, and `@fromContext`.

Members marked `@inaccessible` are omitted, along with everything that references them, matching the client-facing API schema that composition produces.

`@deprecated` is surfaced on operations, fields, arguments, and enum values:

```graphql
type Product {
  sku: String!
  upc: String! @deprecated(reason: "Use `sku` instead.")
}
```

### Merge behavior

When merging multiple files, the first declaration wins for types, members, directive definitions, root operation types, and operation examples. Fern reports every discarded declaration, naming the files involved.
