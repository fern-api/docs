Configure the CLI generator as a target with `language: cli` in `sdk-config.yml`. A single SDK Config can describe the CLI alongside SDK targets: `source.specs` lists the OpenAPI specs, `api` holds settings every target shares (such as [auth schemes](/learn/cli-generator/get-started/authentication)), and each target has its own `package`, `generation`, and `output` blocks. CLI-only settings go in the CLI target's `generation` block. An unknown key fails validation instead of being ignored.

```yaml title="sdk-config.yml" {9-19}
schemaVersion: sdk-config/v1
sdkName: My API
sdkVersion: 1.0.0
source:
  specs:
    - id: my-api
      type: openapi
      path: ./openapi.yml
targets:
  - language: cli
    generation:
      binaryName: my-cli
      customCommands: true
      profiles:
        enabled: true
    output:
      delivery: github
      github:
        repository: my-org/my-cli
        mode: pull-request
```

Settings shared with SDK targets, such as `source`, `api`, `package`, and `output`, are documented in the [`sdk-config.yml` reference](/learn/sdks/reference/sdk-config). This page covers the CLI-specific settings and how the shared blocks apply to a CLI.

## CLI generation settings

Set these under `targets[].generation` on the `cli` target.

<ParamField path="binaryName" type="string" toc={true}>
Name of the compiled binary. Determines the executable filename, the Cargo `[[bin]]` target name, and the environment-variable prefix used for [TLS, proxy, and logging settings](/learn/cli-generator/get-started/features#tls-proxies-and-ca-bundles).

When omitted, the generator derives the name from the API definition's display name (kebab-cased). Multi-spec workspaces must set this field explicitly — there is no sensible auto-derivation when multiple specs are present.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      binaryName: contoso
```

The binary name `contoso` produces:
- Executable: `contoso`
- Env-var prefix: `CONTOSO` (e.g. `CONTOSO_CA_BUNDLE`, `CONTOSO_LOG`)
</ParamField>

<ParamField path="crateName" type="string" toc={true}>
Name of the generated Cargo package. Release archives and installers use it. Defaults to `binaryName` when the target delivers to GitHub.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      binaryName: acme
      crateName: acme-cli
```
</ParamField>

<ParamField path="rootGroup" type="string" toc={true}>
Mounts every spec-derived command under one top-level command, leaving the top level free for custom commands. Without it, generated commands are top-level (`my-cli users list`); with `rootGroup: api`, they become `my-cli api users list`.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      rootGroup: api
```
</ParamField>

<ParamField path="customCommands" type="boolean" default="true" toc={true}>
Controls whether the generator produces the custom command infrastructure alongside the CLI binary. When enabled, the output includes:

- A `<binaryName>-types` library crate (typed serde structs)
- A `<binaryName>-sdk` library crate (HTTP client accessible via `ctx.client()`)
- Scaffolding files for user-authored command handlers

Set to `false` to produce a spec-only CLI with no custom command support.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      customCommands: false
```
</ParamField>

<ParamField path="userAgentSuffixFlag" type="string" default="user-agent-suffix" toc={true}>
Renames the global flag (and its derived environment variable) that a downstream consumer uses to append a product token to the generated CLI's [`User-Agent`](/learn/cli-generator/get-started/features#user-agent). Provide the flag's long name without the leading `--`. It must be a kebab identifier matching `^[a-z][a-z0-9-]*$` and can't collide with a built-in flag name.

Any kebab identifier is accepted except the CLI's built-in flag names (`params`, `output`, `json`, `format`, `dry-run`, `base-url`, `page-all`, `page-limit`, `page-delay`, `no-pager`, `no-extract`, `no-retry`, `no-stream`, `quiet`, `query`, `help`, `debug`, `schema`). The default `user-agent-suffix` exposes `--user-agent-suffix` and `<NAME>_USER_AGENT_SUFFIX`. For example, setting `via` exposes `--via` and `<NAME>_VIA` instead (the environment variable is `<NAME>_` followed by the flag uppercased with hyphens converted to underscores):

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      userAgentSuffixFlag: via
```

A consumer of the generated `contoso` CLI then appends its product token with the renamed flag:

```bash
contoso plants list --via "partner-app/3.1"
# sends User-Agent: contoso-cli/1.4.0 partner-app/3.1
```
</ParamField>

<ParamField path="splitTypeCrates" type="boolean" default="false" toc={true}>
Splits the generated types into one crate per API, plus a shared `core` crate for types that more than one API references, nested inside `<binaryName>-types/crates/`. By default, every generated model lands in a single `<binaryName>-types` crate.

Enable it for workspaces with many specs, where that single crate is one `rustc` compilation unit large enough to exhaust the memory of a standard CI runner and get `cargo build` killed. Splitting also shortens builds, because the per-API crates compile in parallel and cache independently. `<binaryName>-types` remains as a facade that re-exports everything, so imports such as `use plant_types::Plant;` keep resolving and [custom command](/learn/cli-generator/get-started/custom-commands) handlers need no changes. The shipped artifact is the same either way: one binary with every spec embedded.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      binaryName: plant
      splitTypeCrates: true
```
</ParamField>

<ParamField path="profiles" type="object" toc={true} required={false}>
Adds [named profiles](/learn/cli-generator/get-started/authentication#named-profiles) to the generated CLI: a top-level `profiles` subcommand group, a global `--profile` / `-p` flag, and a `<binaryName>_PROFILE` environment variable. A profile stores a tenant's credential, parameter defaults, server URL variables, base URL, retry limit, and default output format once, so users of multi-tenant APIs don't pass an account identifier on every command.

Off by default. A CLI generated without this block is byte-identical to one generated before the option existed, and a `profiles` block with `enabled` unset or `false` is a no-op.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      binaryName: acme
      profiles:
        enabled: true
```
</ParamField>
<Indent>
<ParamField path="profiles.enabled" type="boolean" default="false" required={false}>
Emits the profiles surface. Enabling it adds a top-level subcommand group and a global flag to an existing CLI, which is a surface change for its users.
</ParamField>

<ParamField path="profiles.commandName" type="string" default="profiles" required={false}>
Name of the top-level subcommand group. Must start with a lowercase letter and contain only `[a-z0-9-]`, and can't be one of the built-in groups (`auth`, `completion`, `man`, `errors`, `generate-skills`, `help`). Rename it (for example, to `tenants` or `accounts`) when that reads better for your API. If your spec already declares a `profiles` resource, the built-in subcommands are folded into that group rather than colliding with it, so renaming is optional.
</ParamField>

<ParamField path="profiles.revokeOperation" type="string" required={false}>
Dotted command path of an operation that revokes a profile's remote credential, such as `iam.keys.remove`. When set, `profiles remove` gains a `--revoke` flag that calls the operation before deleting the profile locally. The operation is invoked with the profile's stored parameters as its arguments, so any parameter it requires must be set on the profile. When omitted, the flag isn't registered.
</ParamField>

<ParamField path="profiles.provisionOperation" type="object" required={false}>
An operation that mints a profile's remote credential (an API key), and how its response maps onto that credential. When set, `profiles create` can call the operation with the credentials already in the caller's environment and store the mapped response fields in the OS keychain without printing the secret. Paired with `revokeOperation`, a profile owns its API key end to end: minted when the profile is created, revoked by `profiles remove --revoke`.

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      binaryName: acme
      profiles:
        enabled: true
        revokeOperation: iam.keys.remove
        provisionOperation:
          operation: iam.keys.create
          credential:
            username: sid
            password: secret
          revokeParameters:
            Sid: sid
```
</ParamField>
<Indent>
<ParamField path="profiles.provisionOperation.operation" type="string" required={true}>
Dotted command path of the operation that creates the credential, in the form `<resource>.<method>` (for example, `iam.keys.create`). Like `revokeOperation`, it's invoked with the profile's stored parameters as its arguments.
</ParamField>

<ParamField path="profiles.provisionOperation.credential" type="map<string, string>" required={true}>
Maps each credential field to the top-level response field that supplies it. The keys are the halves the auth scheme stores: `username` and `password` for basic auth, `client_id` and `client_secret` for OAuth2 client credentials, and `token` for a single-value scheme. At least one field must be mapped, and keys and values may contain only `[A-Za-z0-9_.-]`.
</ParamField>

<ParamField path="profiles.provisionOperation.revokeParameters" type="map<string, string>" required={false}>
Maps each parameter the `revokeOperation` takes to the response field it's read from, such as `Sid: sid` to record the new key's ID. The values are stored on the profile as `credential_parameters` and used only by `profiles remove --revoke`, never as request defaults. They're kept in plaintext profile metadata and shown by `profiles show`, so map identifiers here, never secrets. Without `revokeParameters`, the profile has no record of which key it owns, and `--revoke` can only pass the profile's own parameters.
</ParamField>

<ParamField path="oauthTokenEndpoints" type="map<string, object>" toc={true}>
Custom request and response property names for an OAuth scheme's token and refresh endpoints, keyed by the ID of an `oauth2` scheme in `api.auth.schemes` that has a `client-credentials` flow. Use it when the token endpoint doesn't use the standard OAuth property names. See [OAuth flows](/learn/cli-generator/get-started/authentication#oauth-flows).

```yaml title="sdk-config.yml"
targets:
  - language: cli
    generation:
      oauthTokenEndpoints:
        oauth:
          token:
            requestProperties:
              clientId: username
              clientSecret: password
```
</ParamField>

## Package metadata

The Cargo package's metadata comes from the target's `package` block, documented in the [`sdk-config.yml` reference](/learn/sdks/reference/sdk-config#package). With GitHub delivery, the repository and homepage default from `output.github.repository`. Set the Cargo package name with [`crateName`](#cratename).

```yaml title="sdk-config.yml"
targets:
  - language: cli
    package:
      description: Command-line interface for the Plant Store API
      license:
        type: MIT
      homepage: https://plantstore.dev
    generation:
      binaryName: plant
```

## Output and distribution

The target's `output` block controls delivery. Use `delivery: files` with `path` to write the generated Rust project locally, or `delivery: github` with `output.github` to push it to a repository that builds and releases the CLI. npm publishing goes in `output.publish`, and Homebrew and Scoop go in `output.distribution`. See [Publishing](/learn/cli-generator/get-started/publishing) for the full setup and the [`sdk-config.yml` reference](/learn/sdks/reference/sdk-config#output) for every `output` field.

<ParamField path="output.distribution" type="object" toc={true} required={false}>
Configures the release workflow that builds the GitHub Release archives every generated CLI ships, and adds opt-in Homebrew and Scoop publishing on top of them. The release workflow runs from a tagged release, so `distribution` is honored only when the generator delivers to a GitHub repository through `output.delivery: github`; any other target or delivery mode rejects it. Enabling a channel adds a publish job to the release workflow and the matching install command to the generated README. Each job pushes to a public [tap or bucket repository](/learn/cli-generator/get-started/publishing#configure-distribution-channels) you create, authenticating with either a personal access token per channel or a GitHub App whose credentials you store as repository secrets.

```yaml title="sdk-config.yml"
output:
  distribution:
    homebrew:
      tap: garden/homebrew-tap
      formula: plant
    scoop:
      bucket: garden/scoop-bucket
```
</ParamField>
<Indent>
<ParamField path="output.distribution.githubApp" type="object" required={false}>
GitHub App that the Homebrew and Scoop publish jobs use to mint a short-lived installation token at release time, instead of reading a long-lived personal access token. Declared once for both channels; a tap and a bucket under different accounts each need the App [installed on their own account](/learn/cli-generator/get-started/publishing#configure-distribution-channels), since every job requests a token for the owner of the repository it pushes to. A channel's `tokenSecretName` takes precedence over `githubApp`.
</ParamField>

<ParamField path="output.distribution.githubApp.appIdSecretName" type="string" required={true}>
Name of the GitHub Actions secret holding the App's App ID or Client ID.
</ParamField>

<ParamField path="output.distribution.githubApp.privateKeySecretName" type="string" required={true}>
Name of the GitHub Actions secret holding the entire contents of the App's private key `.pem` file, line breaks included.
</ParamField>

<ParamField path="output.distribution.githubAttestations" type='"auto" | boolean' default="auto" required={false}>
Whether the release workflow signs the GitHub Release build artifacts with [GitHub artifact attestations](https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds). GitHub supports attestations on private repositories only with GitHub Enterprise Cloud; on any other private repository the attest step fails every build and no release is cut.

- `"auto"`: attests on public repositories and skips the step on private ones.
- `true`: always attests. Set this for a private repository on GitHub Enterprise Cloud, where `"auto"` would skip attestations that work.
- `false`: never attests. Removes the attest step and its `attestations: write` permission from the release workflow and sets `github-attestations = false` in `dist-workspace.toml`.

```yaml title="sdk-config.yml"
output:
  distribution:
    githubAttestations: false
```
</ParamField>

<ParamField path="output.distribution.homebrew.tap" type="string" required={true}>
Tap repository as `<owner>/<repo>`, such as `garden/homebrew-tap`. The repository must already exist and be public.
</ParamField>

<ParamField path="output.distribution.homebrew.formula" type="string" required={false}>
Formula name, which is also the `.rb` filename `brew install <tap>/<formula>` resolves against. Must start with a lowercase letter and contain only `[a-z0-9-]`. Defaults to `binaryName`.
</ParamField>

<ParamField path="output.distribution.homebrew.tokenSecretName" type="string" default="HOMEBREW_TAP_TOKEN" required={false}>
Name of the GitHub Actions secret holding a token with write access to the tap repository. The workflow's built-in `GITHUB_TOKEN` is scoped to the CLI repository and is rejected here.
</ParamField>

<ParamField path="output.distribution.scoop.bucket" type="string" required={true}>
Bucket repository as `<owner>/<repo>`, such as `garden/scoop-bucket`. The repository must already exist and be public. The generated manifest declares a `64bit` architecture only.
</ParamField>

<ParamField path="output.distribution.scoop.tokenSecretName" type="string" default="SCOOP_BUCKET_TOKEN" required={false}>
Name of the GitHub Actions secret holding a token with write access to the bucket repository.
</ParamField>
</Indent>
