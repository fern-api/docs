---
title: 'CLI version policy'
description: 'Set an organization-wide minimum, maximum, or exact Fern CLI version so every project builds with a consistent CLI.'
subtitle: 'Keep every project in your organization on a consistent Fern CLI version.'
---

Each Fern project pins its own CLI version in [`fern.config.json`](/learn/sdks/overview/project-structure#fernconfigjson). Across many repositories those pins drift apart, so the same API definition can compile against different CLI versions. An organization-level version policy constrains all of them: set a minimum version (a floor), a maximum version (a ceiling), an exact pin, or a range.

The policy is stored on your organization, so it applies to every project without editing any `fern.config.json`.

## Behavior

Fern resolves the version your project would otherwise run, then brings it into the organization's range before running the command.

| Version pinned in `fern.config.json` | Version that runs |
|---|---|
| Below the minimum | The minimum |
| Above the maximum | The maximum |
| Inside the range | The pinned version, unchanged |
| Any version, when the policy is an exact pin | The pinned version from the policy |

The project keeps its own pin: a policy changes which version runs, not what's in `fern.config.json`.

When the version changes, the CLI prints which bound applied before the command proceeds:

```plaintext
Org "acme" requires Fern CLI >= 5.40.0 — running 5.40.0.
Org "acme" caps Fern CLI at <= 5.50.0 — running 5.50.0.
Org "acme" requires Fern CLI between 5.40.0 and 5.50.0 — running 5.40.0.
Org "acme" pins Fern CLI to 5.45.0 — running 5.45.0.
```

A version already inside the range prints nothing.

## Set the policy

`fern org set cli-version` writes the bounds. It requires an organization admin and an authenticated session from [`fern login`](/learn/cli-api-reference/cli-reference/commands#fern-login). The organization is read from `fern.config.json`; pass `--org` to target a different one.

```bash
# Pin an exact version (sets the minimum and maximum to the same version)
fern org set cli-version 5.45.0

# Minimum only: older projects are bumped up, newer ones are left alone
fern org set cli-version --min 5.40.0

# Maximum only: newer projects are capped, older ones are left alone
fern org set cli-version --max 5.50.0

# Both ends in one command
fern org set cli-version --min 5.40.0 --max 5.50.0
```

Each bound is an exact published version of the [`fern-api` package](https://www.npmjs.com/package/fern-api?activeTab=versions), such as `5.45.0` or `5.45.0-rc0`.

`--min` and `--max` update only the bound you pass. Setting `--min 5.40.0` on an organization already pinned to `5.45.0` leaves the maximum at `5.45.0`, turning the pin into the range `5.40.0` to `5.45.0`.

## Read the policy

```bash
fern org get
fern org get --json
```

The default output describes the policy in one line (`Fern CLI pinned to 5.45.0`, `Fern CLI must be between 5.40.0 and 5.50.0`, `Fern CLI must be at least 5.40.0`, or `Fern CLI must be at most 5.50.0`), or reports that no policy is set. `--json` returns the raw `cliVersionMin` and `cliVersionMax` fields.

## Clear the policy

```bash
# Remove both bounds
fern org unset cli-version

# Remove one end, keeping the other
fern org unset cli-version --min
fern org unset cli-version --max
```

## Interaction with `fern upgrade`

A policy changes the version that runs, not the version on disk, so a project stays out of range until it's upgraded. [`fern upgrade`](/learn/cli-api-reference/cli-reference/commands#fern-upgrade) brings the file itself into range: it resolves an upgrade target as usual, then applies the bounds to that target before writing it.

| Version in `fern.config.json` | Policy | Version written by `fern upgrade` |
|---|---|---|
| `5.30.0` | Minimum `5.40.0` | `5.40.0` or higher |
| `5.30.0` | Maximum `5.50.0` | At most `5.50.0` |
| `5.60.0` | Maximum `5.50.0` | `5.50.0` |
| `5.30.0` | Pinned to `5.45.0` | `5.45.0` |

An explicit `--version` outside the range is treated the same way: the bounds win over the requested version.

Running a newer CLI does not apply the migrations that `fern upgrade` performs. Raising the minimum across a major version therefore still requires each project to run `fern upgrade`.

<Note>
A policy never blocks a command. When the CLI can't read your organization's bounds, such as when it isn't authenticated or can't reach Fern, the project runs its own pinned version.
</Note>
