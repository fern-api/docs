<Markdown src="/snippets/enterprise-plan.mdx"/>

When you define a webhook signing scheme, in your API spec or [API-wide in `generators.yml`](#configure-api-wide-in-generatorsyml), Fern automatically generates utilities that allow your SDK users to verify webhook signatures and ensure events originate from your API. These helpers are generated for the TypeScript, Python, Java, Go, PHP, Ruby, C#, and Rust SDKs. The Rust SDK supports HMAC verification configured in the API spec only; it doesn't read the API-wide scheme.

Fern supports two signature verification methods:
- **Hash-based Message Authentication Code (HMAC)** — Symmetric key verification using shared secrets
- **Asymmetric** — Public key verification using RSA, Elliptic Curve Digital Signature Algorithm (ECDSA), or Ed25519 keys

## Generated SDK behavior

The generated SDK exposes a `WebhooksHelper` class with a static `verifySignature` method that returns whether the request is authentic. It takes the raw request body, the signature header value, the signing key (a shared secret for HMAC, a public key for asymmetric verification), and one parameter per additional payload component. A webhook that overrides the document-level configuration gets its own helper, such as `PlantShippedWebhooksHelper`.

These examples verify an HMAC signature over a timestamp and body:

### Verify a request with a per-request algorithm

Some providers send the HMAC algorithm, and optionally a key ID, in a separate header on each request instead of signing with one fixed algorithm. When the signing scheme configures [`algorithm-header`](/learn/api-definitions/ferndef/webhooks#algorithm-headerheader), `WebhooksHelper` also exposes a request-level helper that reads that header. Nothing changes for schemes without `algorithm-header`.

| Language | Method |
|----------|--------|
| TypeScript | `verifyRequest` |
| Python | `verify_request` |
| Java | `verifyRequest` |
| Go | `VerifyRequest` |
| PHP | `verifyRequest` |
| Ruby | `verify_request` |
| C# | `VerifyRequest` |

The helper takes the request headers, the raw request body, one parameter per additional payload component, and the signing key. Header lookup is case-insensitive. The helper reads the signature header and the algorithm header, splits the algorithm header on the configured `key-id-delimiter`, and maps the remaining value to an HMAC algorithm through `algorithms`. For key/value settings headers such as `key=<id>,algorithm=HMAC_SHA256`, setting [`key-id-parameter` and `algorithm-parameter`](/learn/api-definitions/ferndef/webhooks#algorithm-headeralgorithm-parameter) makes the helper read the key ID and algorithm from those named parameters instead. When the algorithm header is absent, it falls back to the configured `algorithm` with no key ID. It then delegates to `verifySignature`, and returns `false` when the signature header is missing, the algorithm value isn't listed in `algorithms`, or no signing key resolves.

The signing key is either the secret itself or a resolver callback that receives the key ID from the algorithm header and returns the matching secret, so the SDK never holds a key store. In Go, the key is always a resolver of type `func(keyID string) (string, error)`, which receives an empty key ID when the header is absent. Java provides overloads for a `String` key and a `Function<String, String>` resolver.

These examples verify a request signed over the notification URL and body, resolving the secret from the key ID:

<Tabs>
<Tab title="TypeScript" language="typescript">
```typescript
import { WebhooksHelper } from "my-api";

const isValid = await WebhooksHelper.verifyRequest(
  request.headers,
  requestBody,
  notificationUrl,
  (keyId) => (keyId != null ? signingKeys[keyId] : process.env.WEBHOOK_SECRET),
);
```
</Tab>
<Tab title="Python" language="python">
```python
from my_api import WebhooksHelper

is_valid = WebhooksHelper.verify_request(
    headers=request.headers,
    request_body=request_body,
    notification_url=notification_url,
    signature_key=lambda key_id: signing_keys.get(key_id) if key_id else os.environ["WEBHOOK_SECRET"],
)
```
</Tab>
<Tab title="Go" language="go">
```go
import myapi "github.com/example/my-api-go"

isValid, err := myapi.WebhooksHelper{}.VerifyRequest(
	request.Header,
	requestBody,
	notificationURL,
	func(keyID string) (string, error) {
		if keyID == "" {
			return os.Getenv("WEBHOOK_SECRET"), nil
		}
		return signingKeys[keyID], nil
	},
)
```

## Setting up webhook signature verification

Configure signature verification in your API definition with the [`x-fern-webhook-signature` extension](/learn/api-definitions/openapi/endpoints/webhooks#sdk-signature-verification), at the document level (inherited by all webhooks) or per-webhook.

## Configure API-wide in generators.yml

If every webhook your API sends is signed the same way, declare the scheme once under [`api.settings.webhook-signature`](/learn/sdks/reference/generators-yml#settingswebhook-signature) in `generators.yml` instead of in the API definition. Every generator in the API emits the shared `WebhooksHelper` from this scheme, even when the spec models no webhooks and carries no `x-fern-webhook-signature` extension. This fits providers such as Twilio, which signs every webhook identically but doesn't model incoming webhooks in its OpenAPI specs.

The block accepts the same [configuration options](/learn/api-definitions/openapi/endpoints/webhooks#sdk-signature-verification) as a webhook signature block in the API definition, including [`algorithm-header`](#verify-a-request-with-a-per-request-algorithm) for providers that select the HMAC algorithm per request:

```yaml title="generators.yml"
api:
  specs:
    - openapi: ./openapi.yml
  settings:
    webhook-signature:
      type: hmac
      header: X-Twilio-Signature
      algorithm: sha1
      encoding: base64
      payload-format:
        components: [notification-url, body]
        delimiter: ""
        body-sort: alphabetical
      body-hash-binding:
        algorithm: sha256
        encoding: hex
        location:
          type: query-parameter
          name: bodySHA256
      url-normalization:
        port-variants: true
        legacy-query-encoding: true
```

When the API definition also configures signatures, the more specific scheme wins: a webhook's own `signature` overrides a document-level `webhook-signature` or `x-fern-webhook-signature`, which overrides `api.settings.webhook-signature`. A webhook with a distinct scheme still gets its own helper, such as `PlantShippedWebhooksHelper`; the API-wide scheme always backs the default `WebhooksHelper`.
