## 3.106.1
**`(fix):`** The generated API error's `requestId` getter now works without configuration for
APIs that return the request ID under a vendor-specific header: it reads
`X-Request-Id` and otherwise falls back to the first response header whose name
ends in `request-id` / `requestid` (e.g. `Twilio-Request-Id`, `x-amzn-RequestId`).
Removed the `requestIdHeader` config option introduced in 3.106.0.


## 3.106.0
**`(feat):`** The generated API error class's `requestId` getter now reads the canonical
`X-Request-Id` header (previously the lowercase `x-request-id`), matching the
casing of every other header the SDK emits. Added the `requestIdHeader`
config option so SDKs can point `requestId` at a different response header,
e.g. `requestIdHeader: Twilio-Request-Id`.


## 3.105.2
**`(fix):`** The generated `WebhooksHelper` now consumes `algorithm-header` from `api.settings.webhook-signature`:
a request-level `verifyRequest` helper reads the configured signature header first (missing or empty
fails early with "could not run: missing signature header"), then the algorithm-selection header
(e.g. `X-Twilio-Webhook-Signature-Settings: <key_id>;HMAC_SHA256`) to pick the HMAC algorithm from
the configured wire values and hand the key ID to an application-supplied secret resolver. When the
header is absent the configured default algorithm and the plain secret are used, so legacy
auth-token flows keep working. The lower-level `verifySignature` is unchanged and still returns
`false` without throwing.
