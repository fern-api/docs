title: Demo Guide

This guide outlines a general structure for demoing Fern's products. Tailor each demo to the customer's specific needs — whether they're switching from a competitor, building docs from scratch, or evaluating SDKs.

## General principles

- **Set an agenda** at the start of the call. Confirm with the customer that the agenda works for them, and ask if they want to add or skip anything. This builds trust.
- **Show the beauty first, then the mechanics.** Lead with the polished output, then show how it's made.
- **Pause for questions.** After each major section, pause and check in.
- **Give your opinion.** After answering questions, share your perspective on why Fern's approach works.

## Docs demo flow

### 1. Show the published docs

Start with a live customer site to showcase Fern's key differentiators:

- Beautiful components and landing pages
- SDK code snippets
- Interactive API Playground

**Pause for questions.**

### 2. Show how it's made

Walk through the configuration files:

#### `docs.yml`
- Explain that `docs.yml` is the backbone of the navigation structure.
- **Live edit**: Show how to add or edit a Markdown page in real time.
- Walk through the git workflow: branch → change → PR → merge.
- Alternatively, demo local development with `fern docs dev`.

**Pause for questions.**

#### `generators.yml`
- Use this as a segue into SDKs.
- Show how SDK snippets are referenced through the package name in the config.

## SDKs demo flow

### 1. Show the generated SDK

Walk through a generated SDK repository:

- Logical file structure and overview of main components
- The auto-generated README (highlight features like retries with backoff built into the SDK)
- The `.fernignore` file for adding custom code to the SDK

**Pause for questions.**

### 2. Show how it's made

Return to `generators.yml`:

- Show the package name configuration
- Highlight features like `overrides.yml` and the `origin` parameter

**Pause for questions.**
